Sweep D — scale & layout

Ten labs, one feed. Every page reads the committed example estate templates/center/shell/example/codebase-graph-station/c4-graph.js through one shared adapter (_kit.js), so what differs between labs is the library, never the input. Open any lab from file:// — no server, no network.

The finding that reorders the question. At 1,399 nodes this station is not renderer-bound. Every library here draws the graph. What they differ on is when the layout is paid for and whether the 9 entity hulls are a first-class object. graphviz sfdp lays out the whole estate in 550 ms server-side and the onyx-scale stand-in in 1.66 s — once, at emit time, next to the generator that already writes the feed. Every in-browser force layout in this sweep costs 1.8 s to 12 s of the reader's time on every page load to reach a worse picture.

The labs

1 — cosmos.gl l2fullonyx

@cosmos.gl/graph 3.4.1 · MIT · OpenJS incubating · 681 KB IIFE (bundled from ESM)

A GPU force layout where positions live in float textures and every force step is a shader pass. The feature that matters to us is setPointClusters() + simulationCluster: the 9 entity hulls become a force the GPU enforces, not a polygon drawn afterwards.

The licence trap: the package you would reach for by name, @cosmograph/cosmos, went MIT at 2.0.0-beta.20 (2024-12-19) and back to CC-BY-NC-4.0 at 3.4.0 (2026-07-30). The MIT continuation is @cosmos.gl/graph, under the OpenJS Foundation. Use that name.

2 — d3-force in a Blob Worker l2fullonyx

d3-force 3.0.0 · ISC · 15 KB bundled with its d3 deps

The CPU baseline, and the cheapest possible change to what we ship today. The file:// constraint every worker option inherits is proven here: a worker cannot fetch(), importScripts() or load a relative path from an opaque origin. The solver ships inside the page as inlined worker source text, or not at all.

3 — ngraph.forcelayout → raw three.js l2fullonyx

ngraph.forcelayout 3.3.1 · BSD-3 · 37 KB + our existing 1.6 MB 3d-bundle

Layout engine and renderer fully separated: ngraph owns positions only (n-dimensional — the same solver does 2D, 3D or higher), and every pixel is ours. 1,404 nodes and 5,530 edges in two draw calls (THREE.Points + THREE.LineSegments) plus a real ConvexGeometry hull per entity. This is the direct answer to "is raw three.js viable" from the layout side: yes, and we own the clock, which 3d-force-graph currently does not let us do.

A vendoring trap found here: ngraph.forcelayout picks its default node-mass function off graph.version > 19; the vendored UMD build of ngraph.graph does not carry that marker, so it reads .length on a Set and throws "Node mass should be a number" on the first step. Own the function.

4 — graphology + ForceAtlas2 l2fullonyx

graphology 0.26.0 + graphology-layout-forceatlas2 0.10.1 · MIT · 74 + 19 KB

ForceAtlas2 separates communities harder than d3-force does, which is what a 9-entity map wants: territories, not a hairball with colours in it. It is also the only off-thread layout in this sweep that works from file:// with nothing inlined by us — its worker is built from a Blob of a stringified function.

There is no WebGL/GPU ForceAtlas2. The package ships one worker utility and it is a plain CPU web worker with Barnes-Hut (O(n log n)); the upstream docs mention no GPU path, present or planned. What is WebGL in this stack is sigma's renderer, not the layout.

Cost noted: graphology is a simple graph by default; 121 parallel edges (363 at onyx) are silently dropped on this feed. Maintenance: FA2 last shipped 0.10.1 in 2022-10 and an 0.11.0-rc1 has sat since 2024-11, but the graphology monorepo is active (1.7k stars, pushed 2026-09-02) and core shipped 0.26.0 on 2025-01-26.

5 — cytoscape + fcose l2fullonyx

cytoscape 3.34.2 + cytoscape-fcose 2.2.0 · MIT · 435 + 126 KB

The only option where the 9 hulls have an identity: cytoscape compound nodes are real parents that own their children, that the layout keeps its children inside, and that you can collapse, drag and style. Everything else in this sweep draws a polygon after the fact.

The cost is the model: one JS object per element with per-element hit-testing. Model build is 4-8 ms and mount 344-779 ms, but fcose itself takes 5.3 s at full and 47.1 s at onyx — and it blocks the main thread so completely that DOMContentLoaded does not fire for 48 s. cytoscape-fcose last shipped 2.2.0 in 2023-01 (repo pushed 2026-04-17); cytoscape itself is very much alive — 3.34.2 on 2026-08-25, 11.2k stars. The algorithm is Balci & Dogrusoz, IEEE TVCG 2022.

6 — WebCola constrained groups l2full

webcola 3.4.0 · MIT · 79 KB · 2.1k stars · last npm publish 2019-05-10 · repo still pushed 2026-04-30

Groups as a hard constraint: hand it groups: [{leaves, padding}] and constrained stress majorization produces guaranteed non-overlapping group rectangles. It also ships flowLayout('y', gap), which is the shape a request path actually has. The l2 result is the best-looking architecture diagram in the sweep.

And it is the slowest by an order: 10.5 s for 316 nodes on the main thread, and at full it had completed 140 of a 400-tick budget after 60 s without converging. Nothing has been RELEASED in six years, though the repo still takes the odd commit — which is the distinction worth carrying: dormant on npm, not abandoned on GitHub. A layout for hundreds of nodes with good constraints, not thousands.

7 — deck.gl graph-layers l2fullonyx

deck.gl 9.3.11 + @deck.gl-community/graph-layers 9.3.9 · MIT · 1.73 MB IIFE

Its layouts are disqualified, verified in the shipped source. Both force layouts build their worker from new URL('./worker.js', import.meta.url) — dead under file:// and dead in any bundle — and the workers importScripts() over the network: https://d3js.org/d3-force.v1.min.js (d3 v1) and https://cdn.jsdelivr.net/npm/gpu.js@latest/…. GPUForceLayout then runs new GPU.GPU({mode: 'cpu'}) beside a // FIXME remove cpu mode. It is not a GPU layout; it downloads a GPU library to not use it. JSONGraphLoader.parseTextSync throws "not implemented". The repo describes itself as "semi-maintained".

So this lab drives SimpleLayout from our own worker and tests only the RENDERER — where deck.gl is genuinely good: first paint 182 ms and a settled layout in 1.0 s at full, 228 ms / 2.5 s at onyx, 60 fps throughout, and PolygonLayer/TextLayer compose in the same view for hulls and labels.

8 — WebGPU compute-shader force layout l2fullonyx

no library · one WGSL kernel · ~200 lines

Tiled n-body repulsion in workgroup shared memory, springs over a CSR adjacency, integrate — the GraphWaGu structure, written directly. It answers "do we need a GPU-layout dependency at all": on this evidence, no. There is no WebGPU force-layout library worth depending on yet (d3-force-webgpu 4 stars / 8 commits; GraphGPU 34 stars, new in 2026; GraphWaGu is EGPGV 2022 research code).

The cost we would actually pay is our own test harness. file:// IS a secure context, so navigator.gpu exists there. But under this repo's headless flags (--use-angle=swiftshader --enable-unsafe-swiftshader) requestAdapter() returns null. Adding --use-webgpu-adapter=swiftshader --enable-unsafe-webgpu --enable-features=Vulkan brings adapter and device up. Adopt WebGPU and every tests/<battery>/run.sh render proof must change, or it goes quietly blind.

9 — precomputed server-side layout l2fullonyx

graphviz sfdp / neato · EPL-1.0 · networkx · BSD-3 · 0 KB client

A codebase map is not a live dataset. It changes when the code changes, and the generators already regenerate it. So the layout moves to the emitter: bake-layout.py runs sfdp once and writes two floats per node into the feed. Client layout cost becomes zero; first draw is 17 ms.

What you give up is response — a baked layout cannot react to an expand or a filter. The lab's "live relax" switch shows the honest hybrid: baked positions as the SEED plus a short local relax (grid-bucketed repulsion + CSR springs, no global n-body), because a good layout only has to be fixed where the interaction disturbed it.

10 — LOD, capsules, bundling, label budget l2fullonyx

no library · strategy lab, over lab 9's baked positions

At this size the station is legibility-bound, not renderer-bound. Four moves, each on a switch, each with its cost printed live:

  • disclosure tiers — 20 capsules / +9 entities / +313 backend / +1,077 frontend; the station's existing T0–T3, priced
  • budget guard — window.__uniBudget = 1600 made adjustable, so the threshold can be argued about with a number
  • edge aggregation — 5,530 edges collapse to ~60 weighted inter-group wires; exact, cheap, reversible. Force-directed edge bundling (Holten 2006) is prettier and O(E²) per iteration and buys nothing an aggregate does not
  • label LOD — rank by degree, collision-test in screen space, redo on zoom; labels are the real budget, not nodes

An ESM-only package cannot be loaded from file:// at all. Verified directly: <script type="module" src="./mod.js"> from a file:// page gives "Access to script at 'file:///…' from origin 'null' has been blocked by CORS policy" and the module never runs. Every modern graph library now ships ESM-first, so "vendorable offline" means "we run esbuild on it", not "we copy a dist file" — a build step this repo does not have yet. The same opaque origin blocks a Worker's fetch(), importScripts() and relative new Worker('./w.js'), which is why every off-thread layout here either inlines its solver into the page or ships its worker as a stringified Blob.

Not labbed, and why

Graphistry

pygraphistry BSD-3 · the renderer is not open

The visualization is a hosted GPU service (Graphistry Hub) or a self-hosted GPU server via Docker/Kubernetes; the Python client is open source, the GPU renderer is the product. Every page is an iframe against a server. That is disqualifying twice over here: our pages open from file:// with no network, and a codebase map is not something to send to someone else's cluster.
