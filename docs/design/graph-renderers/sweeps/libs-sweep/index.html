Constraints this sweep MEASURED on file:// (chrome, origin null)

  • ES modules are unusable — hence every candidate must ship a UMD/IIFE build or be esbuild'd. three.js r185 ships no UMD; Babylon, PlayCanvas, A-Frame, deck.gl and regl all do.
  • A classic new Worker('./sim.js') THROWS — "Script at 'file:///…' cannot be accessed from origin 'null'".
  • A Blob-URL worker WORKS, and it can importScripts() a file:// sibling. That is how B2 runs the force layout off the render thread with no server.
  • troika-three-text renders offline only with an inlined font. With no font it fetches cdn.jsdelivr.net/gh/lojjic/unicode-font-resolver and sync() never fires; with font:'./x.ttf' the worker's own fetch is blocked; with the font as a data: URI it renders. Its UMD also needs 5 peer globals.
  • d3-force-3d's UMD needs 5 peer d3 UMDs (dispatch, timer, binarytree, quadtree, octree) — the "12 KB" is 52 KB in practice.
  • WebGPU cannot be proven here. Headless swiftshader exposes navigator.gpu but requestAdapter() returns null — a WebGPU path can never be gated by these proofs.

What the shipped bundle already contains (probed, not assumed)

window.THREE = r185, 441 exports. Present: InstancedMesh · BatchedMesh · LOD · Points · LineSegments. Absent from the export surface: WebGPURenderer, TSL (THREE.Fn undefined), and the fat-line trio (Line2 / LineMaterial / LineSegments2 — grep of the shipped file: 0 occurrences of either).
The WebGPU backend code is nonetheless compiled into the 1.6 MB (three-render-objects imports three/webgpu) — we pay for it and cannot reach it. CORRECTED 2026-09-07 (source-verified): three-render-objects@1.42 declares a useWebGPU ConfigOption, but 3d-force-graph@1.80's stateInit() destructures only {controlType, rendererConfig, extraRenderers} and forwards exactly those three — ForceGraph3D({useWebGPU:true}) is a silent no-op. The single useWebGPU string in the shipped bundle is three-render-objects' own default, not a forward. Reaching WebGPU means patching the wrapper, driving ThreeForceGraph + ThreeRenderObjects directly, or dropping the wrapper.

SWEEP C — the GAME arm · “we might move in that direction”

Six labs render the SAME committed estate as a walkable codebase city (14 districts · 1,390 solids) through one library-neutral adapter, game-city.js. Load-bearing finding: every position is precomputed deterministically from committed data — no force simulation runs at view time. That is what makes a non-JS engine port thinkable at all, and a city you can learn has to hold still anyway.

The constraint that decides it — file-url-probe.html

Before any engine is compared, the station’s hard rule — opens from file://, no server, no network — is measured rather than assumed. Run node probe-file-url.mjs. Result on Chrome 144, 2 of 8 capabilities available:

capabilityofflinewho needs it

A file:// document has the opaque origin null, so every sibling file is cross-origin. <script src> is exempt — which is exactly why the station ships its feed as c4-graph.js assigning window.GABE_C4 rather than as c4-graph.json. Any engine whose loader begins with fetch() of its own .wasm is dead here before its renderer is even discussed.

The data side — export-city.mjs

What the feed would have to become for a non-JS engine to consume it. Measured:

node export-city.mjs            → city.json     14 districts  1,390 buildings   0.41 MB   build 2 ms
node export-city.mjs --mult 3   → city.x3.json  42 districts  4,170 buildings   1.22 MB   build 10 ms
deterministic across rebuilds: YES

The change is a file format, not a model: game-city.js already computes every position deterministically, so baking it is free. A Godot importer is a ~40-line GDScript loop over buildings spawning BoxMesh + BoxShape3D; a Bevy one is a serde struct. Neither can fetch that file from file:// — it would have to be embedded in the export.
