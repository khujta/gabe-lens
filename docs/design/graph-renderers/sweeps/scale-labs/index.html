Sweep D — scale and layout

Eight labs over the same committed feed (the example estate’s c4-graph.js → 1,384 nodes · 4,053 edges · 20 groups), each opening from file:// with no network. The variable in this sweep is the layout, not the renderer: every lab that is not explicitly testing a renderer draws through one shared canvas-2D view, so layout ms and draw ms are separate columns and no engine can win on the wrong half. A ?k=3 switch clones the feed to 4,152 nodes / 12,279 edges — onyx’s ~3.9k drawn size — so every row has a scale reading beside it. All numbers below were measured on this machine (WSL2, Chrome 144 headless, swiftshader, no GPU); vendor claims are labelled as such.

the labs

D1 · precomputed

graphviz fdp-clustered / sfdp / neato · networkx · EPL-1.0 / BSD-3

The layout is baked by a generator-time script and rides the feed as x/y. Client cost is literally zero, the picture is byte-stable across regens — and fdp with cluster subgraphs is the only engine in the sweep that keeps our 9 entities intact.

D2 · d3-force in a Worker

d3-force 3.0.0 · ISC · 14 kB · Blob-URL worker

The engine we effectively already run, moved off the main thread. Positions come back as one transferred Float32Array per frame.

D3 · ForceAtlas2 in a Worker

graphology-layout-forceatlas2 0.10.1 · MIT · 77 kB

sigma.js’s layout half, used standalone with Barnes-Hut on a toggle so the O(n log n) → O(n²) cliff is visible.

D4 · cosmos.gl as a layout engine

@cosmos.gl/graph 3.4.1 · MIT (OpenJS) · WebGL2 · 678 kB

GPU force simulation, then getPointPositions() harvests the result for our own renderer. Entity clusters are a real force here, not a hull drawn afterwards.

D5 · ngraph.forcelayout 3D

ngraph.forcelayout 3.3.1 · BSD-3 · 31 kB · true nD

A physics engine with no renderer at all — the projection is ours. The direct answer to “what drives raw three.js”.

D6 · WebGPU compute shader

hand-written WGSL · no dependency

Tiled all-pairs repulsion in workgroup memory, CSR springs, ping-pong buffers, one readback. Degrades honestly where there is no device — which is here.

D7 · LOD + aggregation

no library · capsules → hubs → full

The strategy lab. T0 draws 20 capsules and ~90 aggregated wires whatever the node count, which is the only thing on this page that is flat in n.

D8 · fCoSE compound

cytoscape 3.34 + fcose 2.2.0 / cola · MIT

The only engine told about our 9 entities: each is a compound parent with its own gravity. Real placement constraints, at a real price.

the measurement that decided it — entity purity

Our map is not a hairball to be untangled; it is 20 groups that must stay legible as groups. So the number that matters is not edge-crossing count, it is entity purity: of each node’s 10 nearest neighbours in the final layout, what fraction belong to its own entity. A layout can have lovely edge lengths and still shred every hull, and only this catches it. The control is the feed’s own group-seeded ring — grouped but not laid out at all.

Every plain force layout scores worse than doing nothing. 0.40–0.48 against a 0.888 control: a force simulation optimises edge length, and edge length is not entity membership, so it actively pulls our entities apart. That reframes the whole sweep — the question is not “which engine settles fastest”, it is “which engine can be told about the 20 groups”. Three can: graphviz fdp (cluster subgraphs, 0.996), cosmos.gl (setPointClusters, a real GPU force), and fCoSE (compound parents). Everything else needs the grouping enforced afterwards, by us.

For contrast on the identical 1,384-node graph: graphviz neato (stress majorization) took 3,181 ms and networkx spring_layout took 16,542 ms — pure-Python Fruchterman-Reingold is 30× slower than sfdp and scores worse on grouping, so it should not be the baking engine. The fdp linearity above is the load-bearing number: 1,638 → 3,296 → 4,904 ms for 1× → 2× → 3× the graph, so the good layout does not price itself out at onyx scale.

what the numbers say

The strongest result in this sweep is that we may not need a browser layout engine at all — and that the best layout is not the fastest one. Our graph is generated, not explored: a regen already walks the whole archmap, and 1.6 s of graphviz fdp on top of that is free. Baking x/y into the feed removes the settle animation, removes the layout library from the bundle, makes the picture deterministic across regens (so a reader’s spatial memory of where pantry sits survives a commit), and leaves every renderer free to be chosen on its own merits. Critically, it is also the only lane that scored 0.996 on entity purity — the browser engines are not merely slower at this, they are worse at it. It is the one option that improves the 3D station and a 2D lane simultaneously.
The one thing precomputation cannot do is respond. Expanding an entity, filtering to a journey, or dragging a node all need a live solver. That is the real division of labour: bake the global layout, run a small local force only inside whatever the user just opened — a 40-node sub-simulation settles in a frame, and d3-force in a worker (D2, 14 kB, ISC) is already enough for it.
If a live global layout is wanted anyway, cosmos.gl is the only lane that did not care about 3× the graph — 5.0 s at 4,152 nodes against 5.1 s at 1,384, because the simulation never leaves the GPU. Two facts make it usable rather than a curiosity: it is MIT under the OpenJS Foundation as @cosmos.gl/graph, and getPointPositions() hands the result back in 0.5 ms, so it can drive our renderer instead of replacing it. Its setPointClusters is also the only place in this sweep where our 9 entities are a force rather than a hull we draw afterwards.
Two lanes are ruled out on evidence. fCoSE gives the nicest grouping semantics — entities as real compound parents with their own gravity — but took 2 minutes 22 seconds at 4,152 nodes on the main thread; that is not a tuning problem, it is the wrong complexity class for this graph. WebGPU is not rejected on merit — the WGSL in D6 is complete and correct — but on this machine Chrome 144 gave requestAdapter() a null in every configuration tried, headless and headed, with and without --enable-unsafe-webgpu. A lane our own render gate cannot execute cannot be shipped behind that gate.

licence trap, stated once

@cosmograph/cosmos and @cosmos.gl/graph are at the same version (3.4.1) from the same lineage, and only one of them is usable: @cosmograph/cosmos is CC-BY-NC-4.0 (non-commercial), @cosmos.gl/graph is MIT — the OpenJS Foundation fork, announced 2025-05-14. Vendoring the wrong package name is a licence problem that looks like a typo. Hosted Graphistry is out for a different and simpler reason: it renders on a server GPU and streams to the browser, which our file://, no-network constraint forbids outright — no amount of licence would fix that.

reproduce

  • python3 bake-layouts.py — re-bakes lab-layouts.js from lab-feed.js. Deterministic; a re-run on an unchanged feed is byte-identical.
  • node probe.mjs — boots every lab under system Chrome, asserts no network request leaves file://, screenshots, and writes probe-results.json. --k=3 repeats at onyx scale.
  • Every lab also takes ?k=2/?k=3 by hand, and each carries its own controls for the knob that matters to it (Barnes-Hut θ, cluster force, LOD tier).
  • The feed is generated by the sibling sweep’s build-feed.py from the committed example estate — one feed across all sweeps, so the pictures are comparable.
